# 分支切换与合并

## 触发约束

- 只有用户在请求中明确写出 `$switch-branch` 时才执行本 Skill。
- 用户未显式调用时，不因“切到 test”“合并分支”等自然语言自动触发。

## 默认边界

- 将执行前的当前分支视为源分支，将用户明确指定的分支视为目标分支。
- 未指定目标分支时先向用户确认，不自行猜测；`test` 只能作为用户明确指定的目标。
- 默认不创建与合并无关的额外提交、不推送远端、不改写历史；合并本身按 Git 默认策略决定是否产生合并提交。只有用户明确要求时才执行 `git push` 或其他额外操作。
- 合并成功并完成验证后默认切回原始分支；只有用户明确要求停留在目标分支时例外。
- 只修改 Git 状态；不顺手清理、格式化或重构代码。

## 执行流程

1. 记录原始分支：

   ```bash
   git branch --show-current
   ```

   同时检查工作区和暂存区：

   ```bash
   git status --short --branch
   ```

   如果存在未提交改动，先停止并告知用户；除非用户明确授权，不要 stash、丢弃或提交这些改动。

2. 确认源分支和目标分支存在且不是同一分支，并检查远端引用。远端存在时先同步目标和源分支的引用：

   ```bash
   git fetch origin <target> <source>
   ```

   如果远端目标分支在本地目标分支之后，先报告差异，不要把过期的本地目标分支作为合并基线。

3. 切换到目标分支：

   ```bash
   git switch <target>
   ```

4. 将源分支合并到目标分支，使用 Git 默认策略；不要未经请求强制 `--no-ff`、rebase 或改写历史：

   ```bash
   git merge <source>
   ```

   如果发生冲突，立即停止，列出冲突文件并等待用户决定。不要擅自编辑冲突、`git merge --abort` 或提交解决结果。若用户授权解决且冲突涉及 Java 文件，先调用 `java-coding-standards` Skill。

5. 合并成功后检查结果：

   ```bash
   git status --short --branch
   git log -1 --oneline --decorate
   git diff HEAD^1 HEAD --stat
   ```

   按改动范围运行最小必要验证。涉及 Java 改动时调用 `java-coding-standards`，并至少运行相关模块的编译或测试；验证失败时报告失败原因，不要用跳过测试或修改代码来掩盖失败。

6. 合并成功后切回步骤 1 记录的原始分支，并再次确认工作区干净；只有用户明确要求停留在目标分支时跳过此步：

   ```bash
   git switch <original>
   git status --short --branch
   ```

7. 最终报告源分支、目标分支、合并结果、验证结果和当前所在分支。若发现远端目标分支在操作期间被其他进程推进，明确报告该外部变化；不要擅自回滚或覆盖远端。

## 失败与安全边界

- 任何切换、抓取或合并命令失败，都保留现场并报告实际 Git 输出。
- 不使用 `git reset --hard`、`git checkout --`、递归删除或强制推送来“修复”流程。
- 不把“合并到目标分支”解释为“发布到远端”；推送必须得到明确授权。
