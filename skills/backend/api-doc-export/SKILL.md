# 接口文档导出

按用户指定的提交范围，找出受影响的 Controller 与接口模型，调用 `scripts/ApiDocExporter.java` 重新导出 Markdown 文档。

## 前提

- 所有命令都在仓库根目录执行。
- 工具随 skill 一起安装，位于本 skill 的 `scripts/` 目录，不依赖项目里有 `tools/` 副本；调用时用它的绝对路径。
- 源码位置自动发现：递归查找项目下所有 `src/main/java`，不依赖模块名，`--dry-run` 输出里的 `[ * ] Class -> 相对路径` 可用来确认扫到了哪些模块。
- 导出目录由仓库根 `.env.local` 的 `api-doc-out=<绝对路径>` 配置。工具报「未配置导出目录」时，让用户补配置，不要自行猜测或新建目录。
- 导出目录是**独立 git 仓库**，与主仓库分开提交、分开推送。

## 第一步：确定扫描范围

用户不会给精确的 git 范围，按说法映射成命令：

| 用户说法 | 命令 |
|---|---|
| 工作区改动（用户没说明时默认） | `git diff --name-only HEAD` + `git ls-files --others --exclude-standard` |
| 最近 N 次提交 | `git diff --name-only HEAD~N..HEAD` |
| 指定两个提交/分支之间 | `git diff --name-only <base>..<head>` |
| 和 master 不同的部分 | `git diff --name-only master...HEAD`（三点，从分叉点起算） |
| 单个提交 | `git show --name-only --pretty=format: <sha>` |
| 多个零散提交 | 对每个 sha 执行上一条，再合并去重 |

只保留 `*.java`。范围含糊时（例如“最近的改动”），先跑 `git log --oneline -10` 列出候选提交，和用户确认后再继续。

## 第二步：筛选需要导出的文件

只把接口表面相关的文件传给导出工具：

- 全部 `**/controller/*.java`
- `**/model/**/*` 下以 `Req` / `Resp` 结尾的类
- `**/dto/**/*Ret.java`（Mapper 查询结果类型，被 Controller 间接引用时）
- `**/entity/*.java`（字段变动出现在接口响应里时）

service / manager / mapper 接口 / util / config / job / 测试 / MQ 改动不需要导出。传了非 Controller 类时，工具会自动反查引用它的 Controller 一并导出；entity 影响面通常很大，先走 `--dry-run`。

## 第三步：执行导出

```bash
java --source 21 <skill 目录>/scripts/ApiDocExporter.java <路径或类名> [<路径或类名> ...]
```

- 路径用仓库相对路径，一次可传多个。
- 参数超过 10 个或包含 entity 时，先加 `--dry-run` 看会导出的 Controller 清单，确认后再正式导出。
- 只改字段名、字段注释、Javadoc 也要导出，文档内容直接来自源码。
- 需要核对字段解析结果时用 `--dump-type <类名>`。

### 标题冲突检查（导出前必做）

文档文件名取自 Controller 的**类注释标题**（`<标题>.md`），工具只在**同一批次**内检测重名，跨批次同名会静默整份覆盖：上一次 A 导出的 `<标题>.md`，会被这次标题相同的 B 整个替换，A 的接口凭空消失，且不会有任何告警。

导出前对每个待导出的 Controller 检查一遍：

1. 取它的类注释标题和 `@RequestMapping` 的路径前缀。
2. 看导出目录是否已存在 `<标题>.md`。
3. 存在时看文件里的 `**Path:**` 前缀是不是当前 Controller 的前缀 —— 不同就是冲突，先别导出。

冲突的处理顺序：

1. 确认导出目录 `git status --short` 干净；不干净先把已有改动交代清楚，否则覆盖后没法用 git 还原。
2. 冲突的两份里挑一份改标题，**先问用户改哪一份**，不要替用户决定。给它的类注释加端/模块后缀（如 `<标题>-管理端`、`<标题>-学员端`），改的是源码注释，改完要让用户确认。
3. 两份都重新导出，确认目录里出现两个文件、原文件内容未被替换。
4. 目标文件和当前 Controller 前缀一致时，正常覆盖即可。

万一已经覆盖：`git -C "<导出目录>" checkout -- "<标题>.md"` 还原后重新处理，不要带着被覆盖的文档提交。

## 第四步：核对结果

- 「已导出 X.md（N 个接口）」里必须包含本次改动涉及的全部接口。
- 「警告 N 条」要逐条确认属预期：未解析类型、非 CommResp 返回、文件名重复、未找到类。非预期告警要回到源码排查，不要直接忽略。
- 抽查导出文件：本次新增/改名的字段、类型、注释是否已经出现在对应 Markdown 中。
- 看导出目录 `git status --short`：只应出现本批次涉及的 `.md`。冒出不相关的 `.md` 改动、或某个文件 diff 大得离谱，基本就是同名标题把它覆盖了，按第三步的冲突处理还原重做。

## 第五步：汇报与提交

汇报这些内容：

1. 扫描范围（实际执行的 git 命令 + 提交列表）
2. 导出的文档文件名与接口数
3. 警告及处理结论
4. 文档仓库的改动清单

导出并核对完成后，默认**在文档仓库提交并推送**：

```bash
cd "<api-doc-out 目录>"
git status --short          # 没有改动则跳过提交和推送
git add -A
git commit -F .commit-msg   # 提交信息取自 .commit-msg，通常为「文档更新」
git push
```

## 常见问题

- 报「文件名重复」：同一批次多个 Controller 的类注释标题相同。拆成两次导出没用，两次会写同一个文件名，只能改其中一份的标题（见第三步的标题冲突检查）。
- 跨批次同名（没有告警）：导出后才发现某个既有文档的接口全变了/少了，就是标题撞车被覆盖，用 `git checkout` 还原并改标题。
- 报「未找到类」：该文件不属于接口表面，从参数里剔除后重跑。
- 修改了接口但没匹配到 controller/model 文件：确认是否只改了 entity 或 Mapper XML，按第二步补上对应文件。
