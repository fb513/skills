# 轻量 TDD

以快速、确定的行为测试驱动业务代码，不把数据库和外部环境带入日常红绿循环。

开始前读取项目提供的领域上下文和相关 ADR，使用项目领域语言命名测试。存在 PRD 或 ticket 时，以其验收标准作为期望值来源。项目提供 Java 编码规范时，同时遵守该规范。

通过公共 seam 断言调用方可观察的业务结果。测试描述“发生了什么”，不固化内部调用顺序或协作者结构；生产代码发生行为等价的重构时，测试应继续成立。

## 默认测试 seam

优先从以下公共方法观察行为：

- Service：业务流程、权限、状态转换、事务前的决策和下层编排。
- Manager：跨 Service 复用的业务规则，或对缓存、外部资源的封装行为。
- Util：纯计算、规范化和日期处理。
- Model/DTO：静态转换和输出语义。

默认直接实例化被测对象，使用 JUnit 5 与 Mockito，不使用 `@SpringBootTest`。简要说明本次选择的 seam；只有多个 seam 会显著改变测试成本或保障范围时才询问用户。

## 边界判断

先判断改动是否修改了边界本身：

| 改动 | 日常 TDD | 额外验证 |
| --- | --- | --- |
| Service/Manager 业务规则 | 快速行为测试 | 通常不需要 |
| Util、Model/DTO 转换 | 普通 JUnit 测试 | 通常不需要 |
| 数据库访问（MyBatis、JPA、JDBC 等） | Mock Repository/Mapper 验证上层行为 | 对应数据库引擎的 SQL 或集成验证 |
| Controller、认证、参数校验、序列化 | Service 行为测试 | Web 层、API 或协议验证 |
| 缓存、TTL、锁、缓存一致性 | Mock 缓存/锁抽象验证业务分支 | 对应缓存实现专项验证 |
| HTTP 客户端、SDK、文件存储及第三方适配器 | 优先 Mock 仓库 adapter 或 port | 本地 stub、契约测试或测试环境验证 |
| 模型、搜索、检索及其他外部能力 | Mock 逻辑能力接口 | 适配器契约或测试环境验证 |
| 消息、事件、回调及重试 | Mock 发布/消费 port 验证业务编排 | Broker 或事件协议专项验证 |
| 配置加载与动态刷新 | 使用固定配置或 Mock 配置边界 | 配置系统专项验证 |
| 事务、动态数据源 | 测试事务前的业务决策 | 数据库集成专项验证 |
| SSE、虚拟线程、异步并发 | 测试生命周期和同步业务决策 | 协议、并发或超时专项验证 |

不要为了满足 TDD 临时建设完整集成环境。边界未被修改时，使用测试替身并保持内循环快速；边界被修改但当前环境无法验证时，明确记录未覆盖风险和所需验证，不能用行为测试冒充集成保障。

## 按工作类型选择反馈循环

按纵向切片推进，一次只实现一个可观察行为；不要先批量写完整功能的所有测试，再统一编写生产代码。红绿循环的证据要求取决于工作类型，不要求为了满足形式人为制造红灯：

### 新增行为

1. 从验收标准选择一个最小业务场景。
2. 使用领域语言编写一个 JUnit 5 测试。
3. 构造最小输入，并为 Mapper、缓存或外部接口设置确定返回值。
4. 运行单个测试，确认它因目标行为尚未实现而失败，而不是因 Spring、网络或数据配置失败。
5. 编写使测试通过的最小生产代码。
6. 重新运行单个测试，确认变绿。
7. 只对当前切片做行为等价的小范围整理，并持续保持测试为绿。

### 缺陷修复

1. 先把用户报告的具体症状缩小为最小可重复场景。
2. 在能复现真实调用路径的 seam 上编写回归测试，并运行确认它因缺陷失败。
3. 编写最小修复，重新运行测试确认变绿。
4. 再运行原始的、未缩小的复现路径，确认修复没有只覆盖测试夹具。

### 重构或补充覆盖

1. 先运行相关既有测试，记录重构前的绿色基线。
2. 通过公共 seam 补充 characterization 或回归覆盖；如果行为已经存在，测试可以直接通过，不要求人为改坏生产代码来制造红灯。
3. 执行行为等价的重构或测试整理。
4. 重新运行同一组测试，确认基线仍然为绿；若需求发生变化，改按“新增行为”处理。

从项目根目录使用项目现有的构建工具优先运行定向测试。Maven 项目示例：

```bash
mvn test -Dtest=<TestClass>
mvn test "-Dtest=<TestClass>#<methodName>"
```

Gradle 项目使用对应的 `test --tests <TestClass>` 或项目已有封装命令。

运行全量测试命令前先检查测试体。若测试集包含人工脚本、共享环境或外部依赖测试，只运行与改动相关的确定性测试，并在交付中如实说明未运行项及原因。

## 断言业务结果

优先断言：

- 返回值和统计结果。
- 项目定义的业务异常及其稳定错误码或错误语义。
- 状态转换和关键字段。
- 是否执行或跳过一项对外业务动作。
- 传递到持久化或外部边界的业务数据。

允许使用 `ArgumentCaptor` 检查待保存实体或待发送消息的关键字段。除非“是否调用”本身就是可观察契约，否则不要只写 `verify(...)`。

期望值必须来自 PRD、领域规则或人工推导的明确常量，不能在测试中复制生产算法重新计算。

优先通过被测公共方法观察结果。除非正在验证持久化边界本身，否则不要绕过公共 seam 查询数据库或读取内部状态来证明行为。

## 测试替身

默认 Mock 数据库 Repository/Mapper、缓存和锁抽象、HTTP/SDK/文件存储 adapter、消息或事件 port、模型/搜索/检索边界、时间和随机数。纯业务 Manager、Util 和转换逻辑优先使用真实对象；不要仅因为它们是自有类或构造复杂就 Mock。封装外部资源的 Manager 可以作为系统边界 Mock。项目没有某类边界时跳过对应规则，不要为了匹配示例引入新技术。

现有代码使用字段注入时，优先使用 `@InjectMocks`；只有 Mockito 无法构造且改造生产代码超出当前任务时，才最小化使用 `ReflectionTestUtils`。不要仅为了测试方便扩大生产代码改动。

完整示例见 [tests.md](tests.md)，替身边界见 [mocking.md](mocking.md)。两份文档中的类型名和 port 均为占位符，应替换为当前项目已有接口。

### 私有实现与历史测试

- 新增测试只通过公共 seam 观察行为，不调用 private 方法或读取 private 字段。
- 使用反射给遗留字段注入依赖，与通过反射调用 private 行为是两类问题。前者只能作为临时装配手段，后者不应成为新测试模式。

## 禁止事项

- 不在默认行为测试中启动完整应用上下文（例如 Spring Boot 的 `@SpringBootTest`）。
- 不连接共享开发、测试或生产数据库。
- 不访问真实缓存、消息系统或公网接口。
- 不硬编码真实业务 ID、Token、手机号或其他敏感数据。
- 不用 `System.out` 代替断言。
- 不测试 private 方法，不通过反射绕过公共 seam。
- 不把内部调用次数、调用顺序或协作者结构当作主要业务契约。
- 不把数据导出、批量修复和线上调用脚本伪装成自动化测试。
- 不为所有未来场景一次性编写大量测试；坚持一条行为一个循环。

## 完成标准

交付前确认：

- [ ] 已选择与工作类型匹配的反馈循环：新增行为/缺陷有目标性红灯证据；重构/补充覆盖有重构前绿色基线，或记录了不适用原因。
- [ ] 新增行为或缺陷的最小实现后，目标测试通过；重构或补充覆盖后，相关基线测试通过。
- [ ] 相关确定性测试通过。
- [ ] 测试通过公共 seam 断言业务结果，没有固化无关实现细节。
- [ ] 测试没有访问真实基础设施或敏感数据。
- [ ] 边界改动的额外验证已执行，或未覆盖风险已明确记录。

当改动了对外可见契约时，除业务结果外还要断言该项目实际定义的契约语义，例如 HTTP 状态/响应头/响应体、消息或事件字段、流式终止信号、序列化格式、持久化字段和错误语义；不要把其他项目的字段名或响应包装格式复制进测试。
