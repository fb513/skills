# 数据库结构变更

**DDL 是人工执行的脚本，应用不会自动迁移 schema。**代码和数据库结构之间没有任何自动校验，一次变更的正确性完全依赖两件事：**改全所有同步点**，并**在目标引擎上真实核验**。

脚本按项目既有约定放置 —— 先看既存 SQL 放在哪个目录并沿用，没有先例时选一处并说明。**写进脚本不等于已执行**，交付时必须明确交代。

开始前读项目的领域上下文和相关 ADR。字段命名和业务口径使用项目领域语言。

## 先探测两件事

不要假设，先确认。这两项决定后面所有步骤怎么走。

**1. 哪个引擎、什么版本。** 从数据源配置的 JDBC URL 确认 —— 不要假设是哪一个，主库是 MySQL、PostgreSQL、Oracle、SQL Server 的项目都常见。多数据源项目还要确认：本次改的是哪一个库、它是什么引擎（**同一项目里各数据源引擎可能不同**）、对应 Mapper 是否用 `@DS` 绑定到了非默认数据源。

版本要落实到小版本段。同一引擎不同版本的能力差别足以改变方案，例如 MySQL 8.0 之前没有 `CHECK` 约束（语法接受但静默忽略）、也没有降序索引。

顺带确认两处容易漏的配置：

- **分页插件的 `DbType`**（如 `new PaginationInnerInterceptor(DbType.MYSQL)`）是硬编码的，必须与实际引擎一致，否则分页 SQL 方言错误。新增数据源时尤其容易漏。
- **既有 schema 用不用外键、触发器、存储过程。** 摸清现状再动手 —— 规则是新增不加，既有的不主动清理（见"不把业务逻辑放进数据库"）。

**2. 各环境是否共用实例。** 比较各 profile 的数据源配置。**dev 和 test 指向同一实例是常见情况**，此时在任一环境写入都会影响另一环境看到的数据，核验方式必须相应收紧。

## 同步点清单

逐项确认，不适用的写明原因：

| # | 位置 | 检查什么 |
| --- | --- | --- |
| 1 | DDL 脚本 | 建表/改列/索引；引擎方言正确；表和列注释完整 |
| 2 | Entity | 字段增删改；`@TableName`、`@TableId` 主键策略、`@TableField` 列名映射；注释与 DDL 语义一致 |
| 3 | Mapper XML | 列名、`resultMap`、upsert 冲突目标、`INSERT` 列清单 |
| 4 | DTO 与转换 | 对外契约字段、`fromEntity` 工厂、领域内 Convertor |
| 5 | 索引与约束 | 业务唯一性必须由唯一索引保证，不能只靠 Service 层校验；不加外键与级联（见下节） |
| 6 | 引擎绑定配置 | 分页插件 `DbType`、类型处理器 |

**漏改 3 最危险**：MyBatis-Plus 的自动 CRUD 跟着 Entity 走，手写 XML 不会。两者会在运行时静默分叉，且编译期不报错 —— 加了字段却漏改 `INSERT` 列清单，走 `BaseMapper` 的路径正常，走自定义方法的路径静默丢数据。

## 不把业务逻辑放进数据库

**默认不加外键约束**，也不加级联、触发器、存储过程、数据库函数和定时事件。引用完整性和业务规则由应用层负责，数据库只负责结构约束和并发正确性。

外键在 Java 后端里代价高于收益：

- **跨库就失效。** 分库分表、多数据源、服务拆分之后，跨库引用根本建不出外键，规则会退化成"部分表有、部分没有"，比统一没有更难推理。
- **强制写入顺序。** 父行必须先落库，批量导入、并行写入、数据回填都被这个顺序卡住，而这些恰好是最需要吞吐的场景。
- **级联删除的影响面不可见。** `ON DELETE CASCADE` 在数据库层静默删掉下游数据，绕过应用层的权限校验、审计和软删除。读代码看不出来会删几张表。
- **高并发下加锁。** 每次写子表都要在父行上取锁校验，父行成为热点，并放大死锁概率。
- **抬高 schema 变更成本。** 带外键的表加列、改类型、换索引都更容易长时间锁表，且 expand–contract 的中间态经常被外键直接挡住。
- **表达不了业务语义。** 软删除的父行、归档表、逻辑失效状态在外键眼里都还是"有效引用"，约束和真实业务规则从此分叉。

**替代做法**：写入前在应用层校验引用是否存在，删除前查有没有下游依赖，跨表一致性由 Service 编排；需要时用定期对账任务兜底，把不一致查出来而不是让写入直接失败。

**数据库仍然要承担的约束**，不要连这些一起省掉：

- 主键、`NOT NULL`、默认值 —— 结构性约束，与业务规则无关。
- **唯一索引 —— 这条不能让给应用层。**并发下"先查再插"存在竞态窗口，唯一性只有数据库能保证。
- 普通索引 —— 查询性能，不是业务逻辑。

`CHECK` 约束和枚举取值范围属于灰区：它们是业务规则，值域一变就要改 DDL，默认放应用层。但如果存在应用之外的写入路径（人工 SQL、其他服务直连、数据导入），保留它作为最后一道防线是合理的 —— 按项目既有约定来，别在同一个库里两种风格混用。

**逻辑删除让外键的保证变成假的。**用 `@TableLogic` 时，被逻辑删除的父行在数据库看来仍是有效行，外键照样放行引用；反过来物理删除父行又会被外键挡住。两套语义直接对撞 —— 这是 MyBatis-Plus 项目尤其不该加外键的原因。级联删除同理：它删的是物理行，绕过 `@TableLogic`，与应用层看到的数据状态分叉。

### 既有外键怎么处理

**不主动清理。**已经存在的外键可能有别的依赖，删除是破坏性变更。规则只约束新增：新表、新列不加外键。确实需要删除既有外键时，按破坏性变更走 —— 先确认没有依赖它的行为，再与用户确认。

## 引擎差异

下表给出两个最常见引擎的取值。**它是查表用的样例，不是可用引擎的清单** —— 目标引擎不在表里（Oracle、SQL Server、SQLite、达梦等）时，逐行去查它自己的文档补齐同样这些维度，尤其是第一行。**不要把表里任一列的行为默认套到未列出的引擎上。**

| 维度 | PostgreSQL | MySQL 8 |
| --- | --- | --- |
| **DDL 事务性** | 在事务内，失败整体回滚 | **隐式提交，不可回滚** |
| 自增主键 | `BIGSERIAL` / `GENERATED AS IDENTITY` | `BIGINT AUTO_INCREMENT` |
| 列注释 | 独立 `COMMENT ON COLUMN` 语句 | 列定义内联 `COMMENT '...'` |
| 布尔 | `BOOLEAN` | `TINYINT(1)` |
| JSON | `JSONB`（可索引） | `JSON` |
| upsert | `INSERT ... ON CONFLICT (cols) DO UPDATE` | `INSERT ... ON DUPLICATE KEY UPDATE` |
| 取回写入行 | `RETURNING` | 不支持，需二次查询或 `LAST_INSERT_ID()` |
| 不阻塞加索引 | `CREATE INDEX CONCURRENTLY`（**不能在事务内**） | `ALTER TABLE ... ALGORITHM=INPLACE, LOCK=NONE` |
| 索引键长 | 无实际限制 | 3072 字节；`utf8mb4` 下长 `VARCHAR` 需前缀索引 `col(191)` |
| 标识符大小写 | 未加引号折叠为小写 | 依 `lower_case_table_names` 与操作系统 |
| 隔离核验单位 | `CREATE SCHEMA` | `CREATE DATABASE` |
| 大表改列 | 多数 `ADD COLUMN` 为元数据操作 | 可能整表重建，考虑 `pt-online-schema-change` / `gh-ost` |

### DDL 事务性决定安全模型

第一行不是普通差异项，它决定脚本怎么写。先判定目标引擎属于哪一类，再动手：

**DDL 可回滚**（如 PostgreSQL）—— 用 `BEGIN; ... COMMIT;` 包住多条 DDL，中途失败整体回滚，schema 不会停在中间态。

**DDL 隐式提交、不可回滚**（如 MySQL、Oracle）—— 每条 DDL 执行即生效，脚本中途失败会留下**半改状态的 schema**，事务包裹给不了任何保护。这类引擎的多步变更必须：

- 一条 DDL 一个可独立重放的步骤，全部写成幂等形式（`IF NOT EXISTS`，或先查 `information_schema` 再改）。
- 脚本里显式标注每步失败后的人工恢复动作，不能依赖回滚。
- 拆得比可回滚引擎更细，宁可多几步。

判不准就当作不可回滚处理 —— 这个方向的误判只是多做几步，反过来会留下半改的库。

## 变更类型与安全顺序

**加列**：可空或带默认值直接加。要 `NOT NULL` 且表非空时拆三步 —— 先加可空列、回填、再加约束。不要一条语句加无默认值的 `NOT NULL` 列。大表上先查差异表最后一行：有的引擎/版本 `ADD COLUMN` 只是元数据操作，有的会整表重建并长时间锁写。

**改列语义或类型**：按 expand–contract 排。加新列与旧列并存 → 双写或回填 → 迁移读取方 → 删旧列。每步都能单独上线且不破坏正在运行的旧版本代码。

**删列或删表**：先全仓库搜确认没有任何引用 —— Entity、DTO/Convertor，以及 Mapper XML 里的手写 SQL（XML 里的列名编译期查不出来，只能靠搜字符串）。不可逆，先与用户确认，并说明是否需要先备份。

**改唯一索引**：先查实库有没有违反新约束的重复数据，再决定替换还是回填。已等价存在的索引变更是 no-op，明确记录为 no-op，不要重复删建。

**加索引**：大表上按引擎选不阻塞写入的方式（见差异表），并确认该写法在目标引擎上有无附加限制 —— 例如 PostgreSQL 的 `CONCURRENTLY` 不能放在事务块里，与"DDL 用事务包裹"的默认做法直接冲突，必须单独成步。

**回填**：数据量大时说明是否分批，避免长事务锁表。

## 实库核验

按变更性质选一种：

**只读核验** —— 确认现状：索引是否已等价存在、有无重复数据、执行计划是否走预期索引。用引擎提供的只读事务把写入能力真正关掉，别只靠自己小心（PostgreSQL `SET TRANSACTION READ ONLY`，MySQL `START TRANSACTION READ ONLY`；没有等价机制的引擎改用只读账号连接）。索引信息优先查标准 `information_schema`，引擎有更完整的自有视图时用它（PostgreSQL `pg_indexes`，MySQL `SHOW INDEX`），按列顺序、唯一性和谓词核对。记录这只代表一个数据快照。

**隔离核验** —— 验证 DDL 脚本本身可执行。先确认目标引擎的独立命名空间是什么粒度（PostgreSQL 是 schema，MySQL 是 database，其他引擎照其模型判断），创建一个带随机后缀的，把脚本中的目标命名空间替换掉，**针对旧表形态**执行完整脚本，结束后整体删除。引擎不支持轻量新建命名空间时，改用一次性容器实例，不要退而在业务库上试。全程不修改业务 schema 或业务数据。

要证明的事情：脚本能从旧形态平滑升级、回填结果正确、旧索引被正确替换、新约束确实拒绝违规数据。并发语义（upsert 是否保留原字段、行锁认领是否只有一个赢家、事务回滚后能否重试）要用**与 Mapper 实际发出的完全相同的语句**在隔离命名空间里验证，不要用手写的近似版本 —— 这些语句的可用性和语义都随引擎和版本变（`SKIP LOCKED` 就不是所有引擎/版本都有），近似版本证明不了线上行为。

**禁止在共享环境上直接跑未经隔离核验的 DDL，禁止为了核验修改业务数据。**核验输出只写结论和计数，不输出端点、库名、用户名或密码。

**DDL 在目标环境的执行由用户负责，不由 agent 代劳。**agent 的职责到"脚本写好、隔离核验通过"为止。把待执行脚本、涉及的表和列、执行顺序、是否需要回填交给用户。

## 测试

Mapper 的 SQL 生成可以用不连库的测试覆盖列清单和冲突目标。业务分支按项目的 TDD 约定在 Service/Manager seam 上 Mock Mapper 验证。

数据库引擎语义（约束、索引、并发、回填）不能用 Mock 冒充，走上面的实库核验，或明确记录未覆盖风险。

## 交付记录

先看项目是否已有存放核验/发布记录的位置并沿用（例如按 feature 分目录的工作区，或 issue 附件），没有先例时选一处并在交付说明里指明。两份记录：

- **实库核验**：核验时间与时区、引擎与版本、环境、隔离方式、每轮结论与计数、已证明的结论清单、过程中遇到的问题。

DDL 是否已在目标环境执行、由谁执行，必须在交付说明里写清楚，不能留给读者推断。

- [ ] 分页插件 `DbType` 与实际引擎一致
- [ ] DDL 使用目标引擎的正确方言；表和列注释完整
- [ ] DDL 里没有新增外键、级联、触发器、存储过程或定时事件
- [ ] 业务唯一性由唯一索引保证（这一条不能让给应用层）
- [ ] 已判定目标引擎的 DDL 是否可回滚；不可回滚时多步 DDL 已拆成幂等可重放的步骤，并写明失败后的人工恢复动作

- [ ] 编译通过，相关定向测试通过
