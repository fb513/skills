# PRD + 功能规格生成器

产品聊完需求说「生成 PRD」，本 Skill 产出两份文档：

- **`prd.md`** —— 为什么做、做到哪、不做什么、哪些方案已经被否决。给产品定稿，给开发判断边界。
- **`spec.md`** —— 用户可见行为的完整契约。开发照着写，不必回来问产品。

**完成的唯一标准：开发拿着这两份文档，结合已有代码和现有技术栈，能直接写出可验收的代码。** 任何还需要开发自己拍板的点——默认值、上限数值、失败提示、越权看到什么、按钮文案——都是本 Skill 没做完。

| 阶段 | 做什么 | 产出 |
|---|---|---|
| 还原历史 | 沿「基于」链读清这个需求的来历 | 对现状的完整认知，只存在内存里 |
| 整理 | 读事实、对话、原型、历史，扫出矛盾与空洞 | 内部整理表，不写盘 |
| 拷问 | 问到扫不出新缺口为止，答完立刻入账 | 追加若干条事实 |
| 生成 | 按模板写文档 | `prd.md`、`spec.md`、`change-summary.md`、锁定原型 |

## 运行前提

**定位本轮要处理的需求目录**，按顺序取第一个命中的：

1. 产品点名了某个需求（如「生成 0002 的 PRD」）→ 用它
2. 当前目录下有多个需求目录 → 取编号最大的一个（编号前缀为四位数字，如 `0010`）
3. 一个都没有 → 停止，提示先运行 `prd-spec-iteration`

**后文的「目标目录」指定位出来的那个 `<四位编号>-*/`。**

定位后校验三件事：`AGENTS.md` 可读、目标目录存在、目录内有 `facts.md`。任一缺失就报告并停止，不猜路径、不新建。

**「基于」列就是上溯的起点**，取需求目录表里本轮那一行（四位编号）：

- 有编号：本轮是那一轮的增量，未变更的条目仍以它为准。
- `—`：到此为止，这个需求没有更早的轮次。
- 整行缺失：索引过期了，回落到「小于本轮编号的最大已存在目录」，并在报告里提醒补行。

## 还原历史

只读上一轮是不够的。要判断「这次改了什么、碰到了谁、哪些结论已经定过」，必须知道这个需求的来历；编号也要按全局取，不能按本轮表内取。

**路径**：本轮是首轮（「基于」列是 `—`）时没有历史可还原，跳过本节，编号从 1 起。否则从「基于」列出发，沿链往上走，直到某行的 `—`；这条链上最早的那份 `prd.md` 是起点。

**读法：顺着前身引用定向读，不通读全文。** 历史目录里有价值的只有四样东西：

1. **首轮 `prd.md`**：读需求表、第 4 节「受影响的上线功能」、`DEC-xxx`、`OS-xxx`、`Q-xxx`，建立这个需求的骨架。
2. **中间每一轮 `prd.md`**：只读需求表（它新增、修改、废止了什么）、第 4 节「受影响的上线功能」、新增的 `DEC-xxx`、它列出的 `Q-xxx`。
3. **被 `← 前身` 指到的 `spec.md` 条目**：只在需要解释某条行为为什么是现在这样时读，读完就停。
4. **编号**：把所有历史文档里出现过的 `R`、`FR`、`BR`、`Q`、`DEC`、`NFR` 扫一遍，取最大值。新增编号 = 最大值 +1。

串完之后手里应当有三样东西，整理和拷问都要用：

- **每个 `R-xxx` 现在的表述**——旧表述只用来解释它为什么变成现在这样
- **已定决策与被否决的选项**——本轮不得重新引入被否决的方案，除非产品明确推翻并记一条 `已确认`
- **历史上列过、但还没有答案的 `Q-xxx`**：把各轮 Q 表累加，减去被后续 `DEC-xxx` 的决策栏点名的那些；以及其中「阻塞」列为 `P1` 的

**历史链上仍列在 `Q-xxx` 表里的 `P1`，不写文档。** 把它们列出来，让产品二选一：先问出答案，或明确说「带着这些往下走」（这句话记成一条事实，报告里标注「历史存在未答的 P1」）。在一份还有未决项的需求上叠加改动，等于把那些未决项默认成本轮的既成事实。

**不读历史轮次的 `facts.md`。** 事实是每轮自己的账，跨轮只看定稿文档。

## 整理

**先补账。** 对话里已经定下、但 `facts.md` 里没有的，先按 `AGENTS.md` 的记账规则追加入账，再读下面四份输入。只追加，不改写已有条目——漏记一条结论，它就会在生成时消失得无声无息。

读四份输入：

| 输入 | 怎么读 |
|---|---|
| `facts.md` 全量 | 按记录顺序读，同一主题以最后一条为准。被 `收口 / 更正` 覆盖过的旧条不再是待定，不要让它在生成时变成 `Q-xxx` |
| 当前聊天上下文 | 只能用能**逐字引用**的部分；引不出原话就放弃，交给拷问去问 |
| 原型 `prototype.html` | 提取页面、状态、字段、交互、角色差异。页面和主要流程分配 `SCREEN-xxx`，有意义的状态分配 `STATE-xxx`。**已有页面的 ID 沿用原编号，不重新分配**，只有新增页面才取新号——重编会让「这次改了哪一屏」永远说不清 |
| 历史链 | 上一步还原出来的现状认知 |

产出**内部整理表**（只在内存里）：

| 事实 | 分类 | 去向 | 矛盾 / 空洞 |
|---|---|---|---|
| L-003 格式仅 CSV | 决策 | R-002 / DEC-001 | — |
| L-005 保留期未定 | 待定 | Q-001 | 空洞：指标无基线 |
| 原型 SCREEN-002 导出历史 | 未认领 | ? | 矛盾：没有任何事实支撑 |

- **分类**：决策 / 约束 / 否决 / 范围外 / 术语 / 假设 / 待定
- **去向**：PRD 的 `R-xxx` / `BR-xxx` / `OS-xxx` / `Q-xxx` / `DEC-xxx`，或 Spec 的 `NFR-xxx`（各前缀含义见文末「编号速查」）。落不到任何位置的写明「不入文档」及原因，不允许空着
- **矛盾**三类：两条事实互相冲突；事实与原型冲突；本轮事实与历史 `R-xxx` / `DEC-xxx` / `OS-xxx` 冲突（如旧决策定了上限，本轮要改）
- **空洞**两类，都要问：
  - **结构空洞**——必填项没有事实支撑：目标、非目标、范围内外、指标基线、角色矩阵、八类边界情况
  - **实现空洞**——开发照着写会卡住的地方。**这一类是本 Skill 的主要产出**，检查点见「拷问 → 实现空洞」那张表

这一步不产出文档；唯一会落盘的动作是补账。拷问时重跑这段扫描。

## 拷问

**时机只有一个：整理完、写文档之前。** 不在聊天过程中穿插提问——界面还会变，孤立提问也看不到全局。聊的时候负责记，生成前负责问。

**问到扫不出新缺口为止。** 一轮答完重跑整理扫描，答出来的新问题进下一轮；扫不出新东西就停。判据是「开发照着写会不会卡住」，不是「问够几个」——不设数量上限，也不为凑轮次再问一遍。产品可以随时叫停或跳题：已答的入账，未答的转 `Q-xxx`。

### 问什么

问题只能来自整理表，外加一类「原型未认领」：

- **矛盾**：两条事实冲突；事实与原型冲突；本轮事实与历史 `R-xxx` / `DEC-xxx` / `OS-xxx` 冲突（如旧决策定了上限，本轮要改）。冲突靠逐条比对发现，不是通读历史。
- **空洞**：必填项没有事实支撑。结构空洞（目标、范围、指标、角色）产品通常已经想过，真正会漏的是「实现空洞」，见下表。
- **原型未认领**：原型里有、但没有任何事实提到过的行为。问「要做还是占位」，不要默认它是需求。

三类之外一律不问。尤其是「你觉得还需要什么」这类开放问题——那不是拷问，是让产品替你想需求。

**实现空洞：开发一动手就会卡住的地方。** 文档看着完整，问题都在这儿：

| 检查点 | 没定会怎样 |
|---|---|
| 默认值与初始态 | 开发自己选一个，验收时说「不是这个意思」 |
| 字段是否必填、取值与长度限制 | 写松了能绕过，写紧了正常用户过不去 |
| 校验失败提示的原文 | 每个开发各写一版，同一个产品三种口吻 |
| 上限的具体数值 | 「合理限制」= 开发拍脑袋，超限行为没人定义 |
| 排序与分页 | 列表第一屏显示什么，取决于谁的实现 |
| 失败后能否重试、从哪开始 | 重试造成重复数据，或者根本没法重试 |
| 越权时看到什么（报错还是藏入口） | 有的藏按钮、有的报错，安全口径不一致 |
| 重复提交的后果 | 连点两次生成两条记录 |
| 中断后已填内容是否保留 | 误触返回，表单清空 |
| 成功后跳哪、列表是否刷新 | 成功了但界面没反应，用户以为失败 |
| 引用的对象已被删除 | 点进去 500，或显示一个空洞的详情页 |

### 怎么问

**开轮先报概览，再逐个问。** 概览只给数量和主题分布，不列全部问题：

> 本轮 7 个问题：范围 1、边界情况 3、权限 2、文案 1。

产品看完可以说「跳到权限那个」「其余记待定」「只问 P1」。一次贴十几条，后面的问题会建立在假设上，答案是假的。

每个问题四部分，缺一个产品就只能尬答：

1. **来源**：具体位置，`L-003`、`SCREEN-002`、`STATE-003`。不写「根据需求」。
2. **问题**：闭合式优先——二选一，或补一个具体值。
3. **推荐答案 + 依据**：依据只能是事实、原型位置或外部材料。**没有依据就写「无法推荐」**；编一个看起来合理的选项，它就会变成产品的默认选择。
4. **影响**：答了会改哪个 `R-xxx` / `FR-xxx` / `OS-xxx`；答不上来会变成哪条 `Q-xxx`。

**答案逐字入账。** 原话进 `facts.md`，不要改写成模型措辞。

### 按影响面排，不按模板章节

1. 改范围的：做不做、给谁做 → `R-xxx` / `OS-xxx`
2. 让验收无法判定的：八类边界情况、页面行为规格里空着的项 → `FR-xxx`
3. 让角色矩阵不完整的：谁能看、谁能改、越权怎样 → 权限表
4. 文案、术语、视觉：最后问。文案要原文，其余多数沿用原型

### 没答案怎么办

- **答不上来就记 `待定`，不追问。** 「不知道」是一条有效事实；逼出来的答案比待定更有害。
- **定不出「本轮按什么执行」的，不是问题，是空洞。** 按 `P1` 处理，定稿前必须有答案——除非产品明确说「带着这个往下走」，并已记成一条事实。
- **扫不出问题就直说没有。** 编出来的问题会以「已确认」的形式进入事实库，这是最难发现的污染。

### 别这么问

- ✗ 「你对这个功能还有什么想法吗？」——无来源、无推荐、无影响
- ✗ 「建议增加导出功能，比较符合用户习惯」——这是塞需求，不是提问
- ✗ 「上限推荐 10 万行，因为业界常见」——「业界常见」不是依据，应写「无法推荐」
- ✗ 一个「按钮文案用哪个词」纠缠三轮——原型已经表达，或记 `待定`
- ✗ 问「这里要不要加个 loader」——这是实现细节，先问「等的时候用户看到什么」

## 生成

所有文件都写在目标目录内。

**写盘前先看目标目录里有没有 `prd.md`。** 有，就问一句：「`0002/prd.md` 已经生成过，这次是重新生成（覆盖这一轮），还是该开新的一轮？」——听到「重新生成」才动手；说「开新一轮」就停下，让产品先运行 `prd-spec-iteration`。

同一轮里反复生成是正常的，这一问不是拦截，是让人看见自己在覆盖什么。**定稿没有字段标记，所以只能问，不能猜。**

1. **列落点清单**（先列，写完 PRD/Spec 后回来逐条核）：本轮 `facts.md` 里每条非 `待定` 事实（`已确认` / `已否决` / `范围外`），要先想好它落在哪个 `R-xxx` / `BR-xxx` / `OS-xxx` / `Q-xxx` / `DEC-xxx` / `NFR-xxx`，或显式标为「不入文档」并说明原因。不允许静默丢弃。

   不是首轮时，这份清单多一列：每条事实碰的是哪个已有 `R-xxx`（碰不到就是新增）。这一列直接决定需求表里写「新增」还是「修改（← 0001/R-003）」，不用另建一份旧文档审查清单。

2. **确定基线原型**（把原型变成「本轮以哪一份为准」）。先看目标目录里有没有 `prototype.html`：

   | 目标目录 | 动作 |
   |---|---|
   | 有（开目录时已从上一轮复制，或产品讨论时自己放的） | 直接用，**不复制、不移动** |
   | 没有，产品说本轮无原型 | 跳过 |

   - **原型不记账，也没有账本可写。** 位置固定是本目录的 `prototype.html`，版本交给 git——生成完提交一次，commit message 写轮次编号，比存哈希更能说明「这一版是什么时候、为什么定的」。
   - 上一轮有原型、本目录却没有，多半是开目录时漏了复制。别默默当成本轮无原型，明确问一句：「上一轮有原型，要复制一份过来改，还是这一轮确实没有原型？」
   - 目标目录那份与上一轮的 `prototype.html` 内容一致时（`diff` 一下），在报告里注明「与上一轮一致，本轮未改动」。这不是错误，只是让人知道原型没动过。
   - 产品另外指定了一份 html 且它不在目标目录内时，复制进目标目录再锁定；目标目录已有另一份时，问清楚哪份是基线原型，不要两份都留着。
   - **不从其他需求目录取 html 当本轮原型。** 要从某份既有原型起步，就在本目录里留一份副本；两轮共用同一个文件会改一处坏两处。
   - 锁定后不再改动：**生成之后原型再有改动，是下一轮的事**，不要就地改这份。

3. 按 [`references/prd-template.md`](references/prd-template.md) 写 `prd.md`，保留全部章节及顺序。

   **不是首轮时**：上一轮的 `prd.md` 全文读，但**只写本轮要动的部分**。读它是为了判断这次改动波及了谁，不是拿它当底稿逐节复制。

   - **需求表只列三种**：本轮新增、被修改、被废止。已上线且本轮未触碰的**不列**——它们不在本轮开发范围内，列进来会把范围撑大，也让开发分不清哪些是重做、哪些是保留。
   - **第 4 节「受影响的上线功能」必须写全**：这次改动波及哪些已上线能力、原来在哪（`0001/R-003`）、要不要回归。漏一条就是一处没人测的回归。这是全文读上一轮唯一的硬产出。
   - **没动的不用写**，也不要为「未变更」留空行或占位行。它们仍然以历史文档为准。
   - 骨架始终来自当前模板，不跟随旧文档的结构。历史 `prd.md` 只读不复制——`cp` 会把当时的表头和变更历史一起带过来。

   **首轮**：按模板从零写。

   **表头一律重置**，不继承上一轮的任何值：

   | 字段 | 填什么 |
   |---|---|
   | `迭代编号` / `基准编号` | 本轮目录名、上一轮的编号（首轮填 `—`） |
   | `原型` | 按第 2 小步的结果；无原型时不填 |
   | `负责人` | 本轮实际情况，不照抄上一轮 |
   | `事实记录` | `facts.md` @ 本轮最后一条 `L-xxx` |
   | `派生规格说明` / `变更摘要` | 本轮路径 |
   | 「12. 变更历史」 | 只写本轮一行，不继承历史 |

   **所有条目都要标来源 `L-xxx`**：本轮新增或修改的写本轮编号；从历史文档原样沿用的（如上一轮列着、本轮继续列的 `Q-xxx`）写 `0001/L-xxx`。

   **新增编号取全局最大号 +1**，不是本轮表内的最大号——按「还原历史」第 4 条扫出来的值取。同号不同义会让追溯链直接错位，比缺号严重得多。

   不是首轮时，「变更历史」那一行要写清与上一轮的关系和幅度（如「基于 0001：新增 2 条、修改 1 条、废止 1 条」）。**不要写「取代 0001」**——本轮是增量文档，未变更的条目仍以 0001 为准，写「取代」会把两边的有效性都搞混。

4. 按 [`references/spec-template.md`](references/spec-template.md) 写 `spec.md`。Spec 只能从**本轮** PRD 派生，不得重新发明范围，**也不得整节拷贝历史 `spec.md`**（仅可作措辞参考）。拷贝会制造部分同步：PRD 改一条，Spec 里受影响的三条只改了两条，而且不会报错。

   Spec 与本轮 PRD 同构：只写本轮新增或修改的行为，本轮没触碰的 FR 不进本文档，仍以历史 `spec.md` 为准。不是首轮时，`FR-xxx` 沿用原编号、修改的在条目末尾标 `（← 0001/FR-008）`、新增的取全局最大号 +1；重编会切断与历史编号的对应关系。

   **每个本轮新增或改动的页面、状态都必须填满「页面行为规格」那张表**，不许留空、不许写「同上」「按原型」。这张表是「开发不用回来问」的全部依据，缺一项就等于把决定权交给实现方。本轮只动了其中一两项时，其余项写「沿用 `0001/SCREEN-002`」——可查，而不是让人猜。

   **每个 `[NEEDS CLARIFICATION]` 必须对应 PRD 中的一个 `Q-xxx` 并注明是否阻塞 `P1`**；PRD 中影响行为的 `Q-xxx` 也要在 Spec 里有对应标记。**这个标记是未完成标记，不是可交付状态**——它出现，说明那条问题连临时口径都定不出来，因此它是 `P1`，报告里要标「未定稿」。定稿的 Spec 里应当为零。除 `NEEDS CLARIFICATION` 外不允许出现「待定」「TBD」。

5. 写 `change-summary.md`：

   - 本轮变化（相对上一轮）；首轮写「首轮」
   - **落点表**：`L-xxx | 状态 | 落点`
   - **未变更项**：不是首轮时用一句话列出本轮没碰的 `R-xxx`（如「未触碰：R-001、R-002、R-005」）。不用逐条展开——它们仍然以历史文档为准
   - **不要用文本 diff 判断未变更**。两份文档结构差异很大（本轮只写改动），`git diff` 会满屏飘红却说明不了任何事。`git diff --no-index 0001/prd.md 0002/prd.md` 在文件有差异时**退出码是 1**，这是正常的，不是失败；Windows 上还会刷 CRLF 警告，忽略即可
   - 未落地条目及原因
   - 待定清单

6. **报告**：首行写 `本轮处理：0002-数据对账｜基于：0001｜原型：已就位`——「基于」照抄需求目录表里本轮那一行，没有更早轮次时填 `—`；「基于」不是编号最大的那一轮时写 `0001（非最新）`，看报告的人要能一眼看出这一轮接在哪。原型一栏只有两种取值：`已就位`（本目录有文件）/ `无`。

   然后是 R/FR/NFR/Q 数量、未落地条目数、没有答案的 `P1` 数，以及**最可能被质疑的三项**。不是首轮时追加一行「基于 0001：新增 X 条、修改 Y 条、废止 Z 条」，与本轮「变更历史」保持一致。

   有 `P1` 没答案、或 Spec 里还留着 `[NEEDS CLARIFICATION]` 时，**首行加上「未定稿」**。这两个标记说的是一件事：这份文档还不能交给开发。

   最后一行给**可实现性结论**：`可实现性：通过 / 有 N 处仍要开发自行决定`。不通过时逐条列出来。

## 禁止事项

- 不把原话加工成需求表述再记进 `facts.md`。
- 不使用引用不出原话的聊天记忆。
- 不在整理阶段写文档；整理表只存在于内存。补账是唯一例外——它只往 `facts.md` 追加。
- 不静默丢弃非 `待定` 事实；修改和废止必须留下前身 ID。
- 不把已上线且本轮未触碰的需求搬进需求表；被这次改动波及的，只出现在「受影响的上线功能」里。
- 不编辑模板文件；不覆盖任何已存在的需求目录。
- 只从上一轮取原型，不改写任何历史目录的内容。
- 不整节拷贝历史 `spec.md`；不重编已有 `FR-xxx`。
- 不让 Spec 重新定义范围或优先级。
- 不在「页面行为规格」里留空、写「同上」或「按原型」——那一格空着，开发就会自己定。
- 不把技术设计、测试用例、缺陷写进产品文档。Spec 写用户可见行为，不写框架、表结构、接口路径和算法。
- 不在没有确认的情况下覆盖已存在的 `prd.md` / `spec.md`——覆盖一份可能已经定稿、开发正照着做的文档，比多问一句昂贵得多。
- 不改 `AGENTS.md` 的需求目录表——补行是 `prd-spec-iteration` 的活。自己判出来的「基于」写进 PRD 表头，并提醒产品补行。

## 编号速查

> 所有 ID 都是「前缀-三位序号」，像 `R-003`、`Q-002`。前缀不是装饰：它决定这个条目能不能被删、要不要跨轮沿用。

| 前缀 | 指什么 | 写在哪 | 编号规则 |
|---|---|---|---|
| `L-xxx` | 一条事实，一笔账 | `facts.md` | 当轮递增，不跨轮 |
| `R-xxx` | 一条需求，用户要的能力 | PRD 5 | 全工作区唯一，跨轮沿用；修改不换号，新增取全局最大 +1，废止号不回收 |
| `S-xxx` / `OS-xxx` | 本轮要做的 / 明确不做的 | PRD 4 | 当轮有效 |
| `G-xxx` / `NG-xxx` | 目标 / 非目标 | PRD 2 | 当轮有效 |
| `BR-xxx` | 一条业务规则 | PRD 7 | 跨轮可被引用 |
| `Q-xxx` | 一条待补依据的问题，本轮口径已定 | PRD 10 | 跨轮沿用原编号；有结论就落成 `DEC-xxx` 并移出本表 |
| `DEC-xxx` | 一条决策，含被否掉的选项 | PRD 11 | 跨轮沿用；被否的方案不得重引 |
| `SCREEN-xxx` / `STATE-xxx` | 一个页面 / 一个有意义的页面状态 | PRD 6 登记，行为写在 Spec | 跨轮沿用，只有新增页面取新号 |
| `FR-xxx` | 一条功能需求，用户可见行为 | Spec | 跨轮沿用，新增取全局最大 +1 |
| `NFR-xxx` | 一条非功能约束 | Spec | 跨轮沿用 |
| `SC-xxx` | 一条成功标准，结果指标 | Spec | 当轮有效 |

三条硬规则：

- **一律三位补零**：`R-003`、`Q-002`、`BR-001`、`S-001`、`OS-001`、`G-001`、`NG-001`、`SCREEN-001`、`STATE-001`、`FR-008`、`NFR-001`、`DEC-001`、`SC-001`、`L-001`。统一位数是为了排序和扫号，不是为了好看——不补零时，字符串排序会把 10 号排在 9 号前面。
- **已有编号不重编**。历史文档里写成 `0001/R-3` 的，引用时照原样写；**新增一律三位**。号是唯一标识，不是显示格式——为了整齐去重编，等于把所有引用打断。
- **`SC-xxx` 不是 `SCREEN-xxx`**。前者是成功标准（结果指标），后者是页面。只看前缀前半段会认错。
