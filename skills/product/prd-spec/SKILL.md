# PRD + 功能需求生成器

本 Skill 负责工作区流程中的「整理与拷问」和「生成 PRD/Spec」两个阶段。记账规则归 `AGENTS.md`，本 Skill 在场时一并执行。

| 步骤 | 触发 | 输出 |
|---|---|---|
| **记账** | 每轮对话后自动判断；规则见 `AGENTS.md` | 追加 `facts.md` 一行 |
| **整理与拷问** | 产品说「生成 PRD」后自动 | 追加若干条事实（多轮，直到收敛） |
| **生成** | 拷问收口后自动 | `prd.md`、`spec.md`、`change-summary.md`、锁定基线原型 |

## 运行前提

**先定位本轮要处理的需求目录**，按顺序取第一个命中的：

1. 产品这句话里点名了某个需求（如「生成 0002 的 PRD」）→ 用它
2. 当前工作目录本身在某个 `<四位编号>-*` 目录内 → 用它
3. 工作区有多个需求目录 → 取编号最大的一个（编号前缀为四位数字，如 `0010`），并在报告首行写明本轮处理的是哪个（格式见第 4 步第 6 小步）
4. 一个都没有 → 停止，提示先运行 `prd-spec-iteration`

**后文的「目标目录」指定位出来的那个 `<四位编号>-*/`。**

定位后校验三件事：`AGENTS.md` 可读、目标目录存在、目录内有 `facts.md`。任一缺失就报告并停止，不猜路径、不新建。

然后读取：

- `AGENTS.md` 的流程与约定（含记账规则与格式）。它优先于本 Skill 的默认行为；冲突时以它为准，并在报告中说明被覆盖的是哪一条。
- 存在更小编号的需求目录时，它是基准迭代。**不读它的 `facts.md`。**

### 确认本轮与基准的关系

`relation` 通常已由 `prd-spec-iteration` 问过并写入 `manifest.yaml`。到这里处理三件事：

- **为 `null` 时补判**：产品开目录时说「还不确定」，现在必须定下来，写完再继续。
- **与本轮 facts 冲突时报告**：facts 里说「独立」，`manifest.yaml` 却写着 `derive`。不要静默改——列出来让产品裁决，改完 `manifest.yaml` 再往下走。
- **`derive` 时确认基准没有未闭环的阻塞项**：读基准 `prd.md` 第 10 节，存在「阻塞」列为 `P1` 且状态为「待解决」的 `Q-x` 就报告并停止，把这些 `Q-x` 列出来。在一份阻塞项还没关的需求上叠加改动，等于把它的未决项默认成本轮的既成事实。产品明确说「就带着这些往下做」时，把这句话记成一条事实再继续，并在报告里标注「基准存在未闭环阻塞项」。
  `independent` 不校验：它只取基准的角色和术语，不继承任何未决项。

| 值 | 含义 | 判定依据 |
|---|---|---|
| `derive` | 本轮是基准的演进 | 出现「改」「加」「调整」基准已有范围的说法 |
| `independent` | 独立需求，最多复用登录与角色 | 出现「独立」「另一条线」「跟 X 没关系」「只复用登录/权限」 |

补判不出来就问一句，**不要默认 `derive`**。没有基准目录时是 `independent`。

### 按 relation 读基准

| | `derive` | `independent` |
|---|---|---|
| 基准 `prd.md` | 全文读，判断本轮触碰了哪些条目、波及了哪些上线能力 | 只读「3. 用户与角色」和「6. 体验要求 → 术语」两节 |
| 基准 `spec.md` | 读，仅作措辞参考 | 不读 |

这个限制在执行读取时生效，不交给后面写文档时自行取舍。独立需求最常见的失败就是把基准的业务范围顺带写进本轮。

同一需求在定稿前可反复生成，只更新本轮文档。要开新一轮变更时，才运行 `prd-spec-iteration` 建新目录。

## 第 1 步 - 记账（每轮）

**规则与格式的唯一权威是工作区 `AGENTS.md` 的「2. 记账」**，本 Skill 不保留副本。在场时一并执行：出现结论性表述就追加一条，拷问答完一条立刻入账。

第 1 步只处理人说过的话。原型改了、但产品没提的部分不在这一步——第 2 步从原型读出来，第 3 步再问。

**本 Skill 不在场时**（例如产品在另一个会话里调原型），同样由 `AGENTS.md` 约束当时在场的 Agent。它没执行时，第 2 步会从聊天上下文兜底，捞不到的变成拷问问题。

## 第 2 步 - 整理

读四份输入：

1. **`facts.md` 全量**。按记录顺序读，同一主题以最后一条为准。
2. **当前聊天上下文**。只能用能**逐字引用**的部分；引不出原话就放弃，交给拷问去问。
3. **原型**。提取页面、状态、字段、交互、角色差异，为页面和主要流程分配 `SCREEN-xx`，为有意义的状态分配 `STATE-xx`。`derive` 时原型是基准的副本，**已有页面的 ID 沿用基准、不重新分配**，只有新增页面才取新号——重编会让「这次改了哪一屏」永远说不清。
4. **基准 `prd.md`**（仅 `derive`，已在运行前提读入；`independent` 时跳过）。逐条比对 `R-x` / `DEC-xx` / `Q-x` / `OS-x`，找出本轮事实与它们的冲突，以及**本轮触碰了哪些条目**——这份判断直接决定本轮 PRD 里写什么、「受影响的上线功能」列什么。

产出一份**内部整理表**（只在内存里，不写盘）：

| 事实 | 分类 | 去向 | 矛盾 / 空洞 |
|---|---|---|---|
| L-003 格式仅 CSV | 决策 | R-2 / DEC-001 | — |
| L-005 保留期未定 | 待定 | Q-1 | 空洞：PRD 指标无基线 |
| 原型 SCREEN-02 导出历史 | 未认领 | ? | 矛盾：无任何事实支撑 |

- **分类**：决策 / 约束 / 否决 / 范围外 / 术语 / 假设 / 待定
- **去向**：PRD `R-x` / `BR-x` / `OS-x` / `Q-x` / `DEC-xx`，或 Spec `NFR-xxx`
- **矛盾**：三类——两条事实互相冲突；事实与原型冲突；**本轮事实与基准 PRD 的 `R-x`/`DEC-xx`/`OS-x` 冲突**（如基准 `DEC-001` 定了上限，本轮要改）。第三类只有 `derive` 时存在
- **空洞**：PRD 或 Spec 的必填项没有任何事实支撑。必检清单：目标、非目标、范围内外、指标基线、角色矩阵，以及 `spec-template.md` 列出的 8 类边界情况

这一步**不写任何文件**。第 3 步每轮重跑这段扫描。

## 第 3 步 - 拷问（多轮）

拷问是多轮的：一轮回答带出新缺口，就再开一轮，直到收敛。细节见 [`references/grill-guide.md`](references/grill-guide.md)。

### 每一轮

1. **扫描**：重跑第 2 步的扫描逻辑，列出当前所有矛盾与空洞。不需要记录「问过哪些」——答案入账后缺口自然消失。
2. **排序取前 10**：按影响面排序，本轮最多 10 个。
3. **先报概览**：「本轮 7 个问题，集中在边界情况和权限。」只给数量和主题分布，不列全部问题。
4. **逐个问**：一次一个，每题带来源、推荐答案及依据、影响。答完立刻入账 `facts.md`。
5. **回答带出的新缺口**进入下一轮候选池。

产品可以随时插话：「跳到权限那个」「其余记待定」「先这样」。已答的入账，未答的按产品的意思处理。

### 什么时候停

| 判据 | 说明 |
|---|---|
| **候选池为空** | 自然收敛，正常结束 |
| **累计已问 ≥ 25 个** | 人的耐受上限。超出的全部转 `Q-x` |
| **本轮新增缺口 ≤ 2 且无 P1** | 只剩零碎，转 `Q-x` |
| **已问 6 轮** | 保险丝：停下核对剩余缺口。无 P1 则结束，有 P1 则请产品裁决 |

**P1 缺口不被静默截断。** 触发上限时若仍有 P1 未闭环，必须报告并让产品二选一：继续问，或记 `Q-x` 并在报告标注「P1 未闭环」。

「25」是上界不是目标，按实际缺口问，不要凑数。

### 收口

- 没有依据就写「无法推荐」，不得编选项。
- 原型里有、但没人说过的行为，问「要做还是占位」，**不要默认它是需求**。
- 扫不出矛盾或空洞时直说「没有需要问的」，不要为了显得有用而编问题。

## 第 4 步 - 生成

以下所有文件都写在目标目录内。`derive` 与 `independent` 在第 1、2、3、4、5 小步走不同分支。

**写盘前先看目标目录里有没有 `prd.md`。** 有，就问一句：「`0002/prd.md` 已经生成过，这次是重新生成（覆盖这一轮），还是该开新的一轮？」——听到「重新生成」才动手；说「开新一轮」就停下，让产品先运行 `prd-spec-iteration`。

同一轮里反复生成是正常的，这一问不是拦截，是让人看见自己在覆盖什么。**定稿没有字段标记，所以只能问，不能猜。**

1. **列落点清单**（先列，写完 PRD/Spec 后回来逐条核）：本轮 `facts.md` 里每条非 `待定` 事实（`已确认` / `已否决` / `范围外`），要先想好它落在哪个 `R-x` / `BR-x` / `OS-x` / `Q-x` / `DEC-xx` / `NFR-xxx`，或显式标为「不入文档」并说明原因。不允许静默丢弃。

   `derive` 时这份清单多一列：每条事实碰的是哪个已有 `R-x`（碰不到就是新增）。这一列直接决定需求表里写「新增」还是「修改（← 0001/R-3）」，不用另建一份基准审查清单。

2. **确定基线原型**（把原型变成「本轮以哪一份为准」）。先看目标目录里有没有 `prototype.html`：

   | 目标目录 | 动作 | 写入 `manifest.yaml` |
   |---|---|---|
   | 有（`derive` 时已由 `prd-spec-iteration` 复制，或产品讨论时自己放的） | 直接用，算 SHA-256；**不复制、不移动** | `ref: ./prototype.html` + 实际哈希 |
   | 没有，产品说沿用基准那份 | 登记指向 | `ref: ../0001-xxx/prototype.html` + 基准文件的实际哈希 |
   | 没有，产品说本轮无原型 | 跳过 | `prototype: null` |

   - **哈希一律现场算，不读基准 manifest 里的值。** 早期目录可能还在用 `prototype_sha256` 的老格式，字段名对不上；而且文件被改过时，manifest 里的旧值反倒会误导。
   - `relation: derive` 却没有 `prototype.html`，多半是开目录时漏了复制。别默默走「沿用」，明确问一句：「基准有原型，要复制一份过来改，还是这一轮直接用它？」
   - 目标目录那份的哈希与基准文件相同时，在报告里注明「与基准一致，本轮未改动」。这不是错误，只是让人知道原型没动过。
   - 产品在本轮讨论中另外指定了一份 html 且它不在目标目录内时，复制进目标目录再锁定；目标目录已有另一份时，问清楚哪份是基线原型，不要两份都留着。
   - **其他需求目录内的 html 一律不进候选**——那属于那一轮的基线原型，拿过来会让两轮共用一份文件，改一处坏两处。
   - `relation: independent` 时 `ref` 不得指向其他需求目录，指到了就判错回问——那等于把上一轮的界面变成新需求的基线原型。
   - `ref` 指向其他目录时，报告首行注明「依赖 0001 目录」——本目录不自包含，引用它时须同时提供被指向的目录。
   - 锁定后不再改动，后续变化属于新需求。
   - **确定后立刻写回 `manifest.yaml`**：`prototype.ref` + `prototype.sha256`。别等到最后——中途失败时，已经确定的基线原型不该丢。

3. 按 [`references/prd-template.md`](references/prd-template.md) 写 `prd.md`，保留全部章节及顺序。需求表、决策记录、待解决问题、范围外都要标注来源 `L-xxx`：本轮新增或修改的写本轮编号；从基准原样沿用的（如仍未关闭的 `Q-x`）写 `0001/L-xxx`。

   - **`derive`**：基准 `prd.md` 全文读，但**只写本轮要动的部分**。读它是为了判断这次改动波及了谁，不是拿它当底稿逐节复制。

     - **需求表只列三种**：本轮新增、被修改、被废止。已上线且本轮未触碰的**不列**——它们不在本轮开发范围内，列进来会把范围撑大，也让开发分不清哪些是重做、哪些是保留。
     - **第 4 节「受影响的上线功能」必须写全**：这次改动波及哪些已上线能力、原来在哪（`0001/R-3`）、要不要回归。漏一条就是一处没人测的回归。这是全文读基准唯一的硬产出。
     - **没动的不用写**。改了的进需求表并写前身；没改的保持沉默，它们仍然以基准文档为准。不要为「未变更」留空行或占位行。
     - 骨架始终来自当前模板，不跟随基准文档的结构。基准 `prd.md` 只读，不复制文件——`cp` 会把基准的表头和变更历史一起带过来。
     - **新增编号取全局最大号 +1**，不是本轮表内的最大号。分配前先扫一遍历史文档；同号不同义会让追溯链直接错位，比缺号严重得多。
   - **`independent`**：按模板从零写，不读基准。

   **表头一律重置**，不继承基准的任何值：

   | 字段 | 填什么 |
   |---|---|
   | `迭代编号` / `基准编号` | 本轮目录名、基准目录编号 |
   | `原型` | 按第 2 小步的结果；无原型时不填 |
   | `负责人` | 本轮实际情况，不照抄基准 |
   | `事实记录` | `facts.md` @ 本轮最后一条 `L-xxx` |
   | `派生规格说明` / `变更摘要` | 本轮路径 |
   | 「12. 变更历史」 | 只写本轮一行，不继承基准历史 |

   `derive` 时「变更历史」那一行要写清与基准的关系和幅度（如「基于 0001：新增 2 条、修改 1 条、废止 1 条」）。**不要再写「取代 0001」**——本轮是增量文档，未变更的条目仍然以 0001 为准，写「取代」会把两边的有效性都搞混。

4. 按 [`references/spec-template.md`](references/spec-template.md) 写 `spec.md`。Spec 只能从**本轮** PRD 派生，不得重新发明范围，**也不得整节拷贝基准 `spec.md`**（基准 spec 仅可作措辞参考）。拷贝会制造部分同步：PRD 改一条，Spec 里受影响的三条只改了两条，而且不会报错。

   Spec 与本轮 PRD 同构：只写本轮新增或修改的行为，本轮没触碰的 FR 不进本文档，仍以基准 `spec.md` 为准。`derive` 时 `FR-xxx` 沿用基准编号、修改的在条目末尾标 `（← 0001/FR-008）`、新增的取全局最大号 +1；重编会切断与基准的编号对应关系。每个 `[NEEDS CLARIFICATION]` 必须对应 PRD 中的一个 `Q-x` 并注明是否阻塞 P1；PRD 中影响行为的 `Q-x` 也要在 Spec 里有对应标记。

5. 写 `change-summary.md`：

   - 本轮变化（相对基准迭代）；`independent` 时写「与基准的关系：独立，仅复用 X」
   - **落点表**：`L-xxx | 状态 | 落点`
   - **未变更项**：`derive` 时用一句话列出本轮没碰的 `R-x`（如「未触碰：R-1、R-2、R-5」）。不用逐条展开，也不用为它们写任何内容——它们仍然以基准为准。
   - **不要用文本 diff 判断未变更**。两份文档结构差异很大（本轮只写改动），`git diff` 会满屏飘红却说明不了任何事。`git diff --no-index 0001/prd.md 0002/prd.md` 在文件有差异时**退出码是 1**，这是正常的，不是失败；Windows 上还会刷 CRLF 警告，忽略即可。
   - 未落地条目及原因
   - 待定清单

6. **报告**：首行写 `本轮处理：0002-数据对账｜relation: independent｜原型：已就位`，原型一栏三种取值——`已就位`（本目录有文件）/ `沿用 0001` / `无`。然后是 R/FR/NFR/Q 数量、未落地条目数、未闭环 P1 数，以及最可能被质疑的三项。`derive` 时追加一行「基于 0001：新增 X 条、修改 Y 条、废止 Z 条」，与本轮「变更历史」保持一致。

## 禁止事项

- 不把原话加工成需求表述再记进 `facts.md`。
- 不使用引用不出原话的聊天记忆。
- 不在整理阶段写文件；整理表只存在于内存。
- 不静默丢弃非 `待定` 事实；修改和废止必须留下前身 ID。
- 不把已上线且本轮未改动的需求搬进本轮 PRD；它们只能出现在「受影响的上线功能」里。
- 不编辑模板文件；不覆盖基准迭代或历史需求目录。
- 不从其他需求目录取原型，也不改写基准目录的任何内容。
- 不整节拷贝基准 `spec.md`；`derive` 时不重编 `FR-xxx`。
- 不让 Spec 重新定义范围或优先级。
- 不在没有确认的情况下覆盖已存在的 `prd.md` / `spec.md`——覆盖一份可能已经定稿、开发正照着做的文档，比多问一句昂贵得多。
- 不把技术设计、测试用例、缺陷写进产品文档。
