## 需求（必填）

### 功能需求

> **覆盖规则。** 每个 `FR-xxx` 至少被一个验收场景引用（场景末尾的 `[FR-001]`）。没被引用的 FR，没人知道怎么算做完——实现方只能自己定一个，返工就是这么来的。拆不出场景就拆细，或标成 `[NEEDS CLARIFICATION]`。
> **可追溯规则。** 每个 FR 必须在括号里注明来源 PRD 需求，例如 `(R-2)`。没有来源的 FR 就是范围蔓延——删掉，或提交给 PM 并记入待解决问题。
> **事实链。** 聊天原话 → 事实 `L-xxx` → PRD `R-x` → `FR-xxx` → 验收场景。任一环断裂即不可归因；排查从最上游的断点修，不要直接改下游文档。
> **编号规则。** 修改已有 FR 沿用原编号，条目末尾标 `（← 0001/FR-008）`；新增的取全局最大号 +1。已有引用按编号索引，重编等于全废。本轮没触碰的 FR 不进本文档。
> 本节只说明产品要做什么。技术实现与架构属于技术设计文档；非功能约束归「非功能需求」；不阻塞验收的结果归「成功标准」。
> 每个 `[NEEDS CLARIFICATION]` 必须对应 PRD 中一个 `Q-x`，并在括号里注明是否阻塞 P1；PRD 中影响行为的 `Q-x` 也要在本文档有对应标记。
