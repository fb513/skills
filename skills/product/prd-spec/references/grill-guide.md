# 拷问指南

## 什么时候问

**只有一个时机：生成 PRD/Spec 之前**，整理完成之后。

不在聊天过程中穿插提问：界面还会变，孤立提问也看不到全局。

## 问几轮

**多轮，但会收敛。** 一轮的回答往往带出新缺口，必须继续问：

> 问：「导出失败时用户看到什么？」
> 答：「提示失败条数，重试从头开始。」
> → 新缺口：「重试从头开始，已成功的部分会不会重复导出？」

单轮就收工，这类问题会留成 Spec 里的 `[NEEDS CLARIFICATION]`。

### 每轮的上限

| 约束 | 值 | 作用 |
|---|---|---|
| 单轮问题数 | **≤ 10** | 一轮太长，答到后面就开始敷衍 |
| 累计问题数 | **≤ 25** | 人的耐受上限，超出全转 `Q-x` |

### 什么时候停

任一成立即结束拷问：

| 判据 | 处理 |
|---|---|
| 候选池为空 | 正常结束 |
| 累计已问 ≥ 25 | 剩余全部转 `Q-x`，在报告里说明 |
| 本轮新增缺口 ≤ 2 且无 P1 | 只剩零碎，转 `Q-x` |
| 已问 6 轮 | 保险丝：停下核对剩余缺口。无 P1 则结束，有 P1 则请产品裁决是否继续 |

**P1 缺口不被静默截断。** 保险丝或累计上限触发时若仍有 P1 未闭环，必须报告并让产品二选一：继续问，或记 `Q-x` 并在报告标「P1 未闭环」。

「25」是上界不是目标，按实际缺口问，不要凑数。

## 问什么

问题**只能来自整理表**，三类：

| 来源 | 判据 | 例子 |
|---|---|---|
| **矛盾** | 两条事实冲突；事实与原型冲突；或本轮事实与基准 PRD 的 `R-x`/`DEC-xx`/`OS-x` 冲突 | 「`L-003` 说格式只给 CSV，`L-006` 说法务要求 XLSX。以哪个为准？」<br>「`0001` 的 `DEC-001` 定了单次上限 1 万行，本轮要加排除规则后重算。是改上限，还是排除后再校验？」 |
| **空洞** | PRD/Spec 必填项没有任何事实支撑 | 「导出失败时用户看到什么？重试安全吗？」 |
| **原型未认领** | 原型里有行为，但没有任何事实提到过 | 「原型里有个『导出历史』入口，这版要做还是占位？」 |

矛盾里的第三种（本轮事实与基准冲突）只在 `derive` 时存在。基准的 `facts.md` 不读，冲突靠它与基准 `prd.md` 的对照发现——所以读基准 PRD 不是通读一遍，是逐条比对 `R-x` / `DEC-xx` / `Q-x` / `OS-x`。

三类之外一律不问。尤其是「你觉得还需要什么」这类开放问题——那不是拷问，是让产品替你想需求。

## 怎么问

**开轮先说一句概览，再逐个问。** 概览只给数量和主题分布，不列全部问题：

> 本轮 7 个问题：范围 1、边界情况 3、权限 2、文案 1。

产品看完可以说「跳到权限那个」「其余记待定」「只问 P1」。列全清单会让产品一次性读七个问题然后草率回答，逐个问才有思考空间。

每个问题必须包含四部分：

1. **来源**：具体位置，如 `L-003`、`SCREEN-02`、`STATE-03`。不写「根据需求」。
2. **问题**：一次一个，优先闭合式（二选一或补一个具体值）。
3. **推荐答案 + 依据**：依据只能是事实条目、原型位置或外部材料。**没有依据就写「无法推荐」**。不要编一个看起来合理的选项——它会变成产品的默认选择，等于替产品做决定。
4. **影响**：答了会改变哪个 `R-x` / `FR-xxx` / `OS-x`；答不上来会变成哪条 `Q-x`。

## 硬规则

- **一次只问一个。** 批量贴问题会让后面的问题建立在假设上，答案是假的。
- **每轮先报后问。** 概览 + 三选一（逐条答 / 只答 P1 / 全部记为待定），不要直接开问。
- **答不上来就记 `待定`，不追问。** 产品说「不知道」是一条有效事实，逼出来的答案比待定更有害。
- **答案逐字入账。** 原话进 `facts.md`，不要改写成模型措辞。
- **数量设上限。** 单轮 ≤10 个、累计 ≤25 个；超出的转 `Q-x`。若被截断的是 P1 缺口，必须在报告里标「P1 未闭环」，不得静默放过。
- **可随时中止或跳转。** 产品说「先这样」→ 已答入账、未答转 `Q-x`；说「跳到权限那个」→ 直接跳，中间的不算问过。
- **扫不出问题就直说没有。** 不要为了显得有用而编问题——编出来的问题会以「已确认」的形式进入事实记录，这是最难发现的污染。

## 提问顺序

按影响面排序，不按模板章节：

1. **改变范围的**：做不做、给谁做 → `R-x` / `OS-x`
2. **让验收无法判定的**：边界情况的 8 类（见 `spec-template.md`）→ `FR-xxx`
3. **让角色矩阵不完整的**：谁能看、谁能改、越权怎样 → 权限表
4. **文案、术语、视觉细节**：最后问，且多数可以不问——原型已经表达了

## 反面示例

- ✗ 「你对这个功能还有什么想法吗？」——无来源、无推荐、无影响，产品只能尬答
- ✗ 「建议增加导出功能，比较符合用户习惯」——这是塞需求，不是提问
- ✗ 一次贴 15 个问题——后面的问题依赖前面的答案，等于白问
- ✗ 「导出上限推荐 10 万行，因为业界常见」——「业界常见」不是依据，应写「无法推荐：事实记录与原型均未涉及」
- ✗ 问完本轮 6 个就收工，尽管回答明显带出了新缺口——那是把问题留给技术去猜
- ✗ 为了凑轮次继续问「按钮文案用哪个词」——这类问题原型已经表达了，或者记 `待定` 即可
