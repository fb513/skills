# 需求流程

本工作区的需求工作分三步，每一步由一个 Skill 或一条约定驱动，不要跳步。

## 1. 开始新一轮需求

**Skill：** `prd-spec-iteration`

产品提出一个新需求，或上一轮已定稿、要开始下一轮时使用。

## 2. 讨论需求并记账

**无对应 Skill**

这一阶段由产品和原型 Agent 自由讨论：聊需求、调整 HTML 原型、推翻重来，工具不限。

唯一的硬要求是记账。上下文会压缩，不记就丢了。

### 记账规则

对话里出现明确的决定、否决、约束、范围外、待定，**当时在场的 Agent** 立即追加一条到当前需求目录的 `facts.md`，并告知编号（如「已记 L-007」）。不需要产品先说「记一下」；产品说了就做一次收口，把这一段散落的结论一并补上。

一行一条，`- L-001 已确认：原话`。三个要素，没有第四个：

| 要素 | 规则 |
|---|---|
| 编号 | `L-001` 起，本迭代内递增，不复用 |
| 状态 | 只有 `已确认` 和 `待定` |
| 内容 | 原话或原话的紧凑转述，冒号后直接接话 |

- **不加工成需求表述。**「想要个导出」不要写成「系统应支持导出功能」——后者是生成阶段的事，提前加工会让原话里的条件、让步、犹豫全部丢失
- **不分类、不判去向。** 不写「这是决策」「这是约束」，不写它属于 `R-x` 还是 `OS-x`
- **粒度是「一个话题收口」，不是逐句。** 连续几个来回才形成结论时，等结论出现再记，不要中途打断
- **拿不准就写 `待定`。** 事后把待定改成已确认，成本远低于事后补漏
- **append-only。** 不删不改；更正追加一条并写明「更正 L-00x」，同一主题以最后一条为准——记录顺序本身就是演进记录
- **只记本迭代说的话，不复制基准的事实。** 编号也只在本迭代内递增，不为对齐基准而跳号

不该记的：原型里长什么样（文件本身就是记录，生成时直接读）、纯背景闲聊、还没形成任何倾向的探索。

本轮与基准的关系通常开目录时已问定、写进 `manifest.yaml`，不用再记。两种例外各记一条：当时答「还不确定」现在有结论了；结论和原来的答案反了。生成时会把冲突列出来让人裁决，不会自己改。

**归属。** `facts.md` 是事实的唯一来源，`prd.md`、`spec.md` 是可再生派生物——事实有误时改事实记录并重新生成，不要直接改文档来修事实。只有记账能写 `facts.md`，其他 Skill 不得整理、补全、去重。

### 原型

**在当前需求目录里，就在那份上改。** 不要动其他需求目录的 `prototype.html`——那是那一轮的冻结件，改一个字节它的哈希就对不上了，而历史目录不可改写。

这一阶段没有结束标志，产品随时可以说「生成 PRD」进入下一步。

## 3. 生成 PRD / Spec

**Skill：** `prd-spec`

产品说「生成 PRD」时进入这一步，产出 PRD、Spec 与变更摘要。

## 约定

- **目录与编号不复用。** 需求目录（如 `0001-订单批量导出/`）一经写入不覆盖、不改写。
- **产品文档不写实现。** PRD、Spec、`facts.md` 不含技术栈、API、数据模型、测试用例和开发缺陷。
- **新增步骤追加到末尾**，不改已有步骤的编号和内容。

## 团队约定

除下列两条外，本工作区特有的规则追加在这里。

- **跨需求长期成立的约束写在这里**，不要留在某一轮的 `facts.md` 里。例：本产品的登录与角色权限由 `0001` 定义，后续需求只引用、不重定义。
- **目录不自包含时要说清楚。** `manifest.yaml` 的 `prototype.ref` 指向其他目录时，本目录不含原型文件，引用本目录须同时提供被指向的目录。
